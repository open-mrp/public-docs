An **audit event** is an immutable record of a single mutation: a resource was created, updated, deleted, restored, archived, approved, or denied. Each event names the actor who did it, the resource it happened to, when it happened, and — when you ask for them — the exact field-level before/after values.

<BetaTag /> All three audit-event endpoints are in **public preview**. They are live and documented
here, but their shape and filter set may change without notice before general availability — see
<InternalLink pathKey="releasePhases" text="release phases" />.

Audit events are the answer to "who changed this order's ship-to address, and what was it before?". They are a different layer from <InternalLink pathKey="api.requestLogs" text="request logs" />: a request log describes one HTTP call, while an audit event describes one business-object change. The two are linked — an event that originated from an API request carries that request log as an expandable sub-object.

## What an audit event records

| Field                           | Description                                                              |
| :------------------------------ | :----------------------------------------------------------------------- |
| `action`                        | `create`, `update`, `delete`, `restore`, `archive`, `approve`, or `deny` |
| `resource_type` / `resource_id` | The record that changed                                                  |
| `actor`                         | The user, API key, or agent identity that performed the mutation         |
| `account`                       | The account the mutation was performed _against_                         |
| `changes`                       | Field-level `old_value` / `new_value` pairs                              |
| `metadata`                      | Arbitrary JSON attached to the mutation, such as a reason code           |
| `request`                       | The request log for the API call that caused the change                  |
| `idempotency_key`               | The idempotency key of the originating request, if one was sent          |
| `source_ip`                     | The originating client IP                                                |
| `occurred_at` / `created_at`    | When the mutation happened, and when the event row was written           |

`approve` and `deny` record a human decision on a gated action — for example allowing or rejecting a review-gated agent tool call.

## Listing events

```bash
curl "API_HOST/v1/core/audit-events?limit=25" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Augno-Version: CURRENT_API_VERSION" \
  -H "Augno-Account: YOUR_ACCOUNT_ID"
```

Results are returned newest-first and use standard cursor <InternalLink pathKey="api.pagination" text="pagination" />. See the <InternalLink pathKey="apiReference.auditEvent.listAuditEvents" text="List Audit Events" /> reference for the full response shape.

Every list is scoped to events where your account is either the **acting** account (it performed the mutation) or the **target** account (the mutation was performed against it). You never see events belonging to unrelated accounts.

## Scoping to a record's entire history

The most useful thing this endpoint does is return a whole **history tree** rather than a single row's changes. Pass `root_resource_type` and `root_resource_id` together and you get every event that was stamped with that root, including events on records that have since been deleted.

```bash
curl "API_HOST/v1/core/audit-events?root_resource_type=sales_order&root_resource_id=or_xxx&include[]=actor&include[]=changes" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Augno-Version: CURRENT_API_VERSION" \
  -H "Augno-Account: YOUR_ACCOUNT_ID"
```

Sales orders are the family this was built for. An order stamps itself as its own root, and so do its lines, picks, pick lines, shipments, shipment lines, and invoices — so one call returns the order's own changes alongside everything audited beneath it, in one newest-first list. This is exactly what the order timeline in the Dashboard renders.

What comes back is whatever of that tree is _audited_, which is not the same as everything that ever happened to the order. Invoices, for example, currently contribute update events only: there is no audited invoice creation or deletion, and invoice lines are not audited at all. Read the result as the recorded history, not as a guarantee of completeness.

Three things to know:

- **Both parameters are required for the filter to apply.** Supplying only `root_resource_type` or only `root_resource_id` does not error; the root filter is simply ignored and you get an unscoped list back.
- **Only two record families stamp a root today, and they behave differently.** A sales order stamps the root on itself and on every descendant. A production schedule stamps it only on _schedule line_ events, and only for changes that fall inside a frozen week — the schedule record's own events carry no root at all. Root scoping a production schedule therefore returns neither the schedule's own history nor line changes made outside the frozen window.
- **Root scoping a type that stamps no root returns an empty list.** The filter is an equality match on _both_ stored columns, so an event that carries no root can never match it. Everything outside those two trees — customers, items, purchase orders, users — falls into this category. You do not get a narrower answer back; you get nothing. Use `resource_types` and `resource_ids` for those records instead.

## Filtering

All filters combine with AND. Array filters accept either repeated bracketed values (`?actions[]=create&actions[]=update`) or a single comma-separated value (`?actions=create,update`).

| Parameter                                 | Description                                                                                                                           |
| :---------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------ |
| `q`                                       | Free-text term matched against `resource_type`, `action`, `resource_id`, and the originating request ID                               |
| `start_date` / `end_date`                 | Restrict to events on or after / on or before an RFC 3339 timestamp                                                                   |
| `resource_types`                          | Restrict to audited resource types, e.g. `sales_order,invoice`                                                                        |
| `resource_ids`                            | Restrict to specific audited record IDs                                                                                               |
| `root_resource_type` + `root_resource_id` | Whole-tree scoping, described above                                                                                                   |
| `actor_ids`                               | Match `actor.id` — a user ID for `user` actors, an API key ID for `api_key` actors                                                    |
| `actor_types`                             | The enum accepts `user`, `api_key`, `agent`, and `group`, but audit events only ever record the first three — `group` matches nothing |
| `actions`                                 | `create`, `update`, `delete`, `restore`, `archive`, `approve`, `deny`                                                                 |
| `actor_account_ids`                       | Narrow to specific _acting_ accounts — for example a customer account that mutated a record on yours                                  |
| `target_account_ids`                      | Narrow to specific _target_ accounts — for example one customer's or supplier's account                                               |

Passing a query parameter this endpoint does not define returns a `parameter_unknown` error rather than being ignored. See <InternalLink pathKey="api.errors" text="Errors" />.

## Expanding sub-objects

Audit events return their sub-objects as `null` unless you ask for them with <InternalLink pathKey="api.include" text="include" />. Five values are accepted:

- `account` — the account the mutation was performed against
- `actor` — the user, API key, or agent that performed it
- `changes` — the field-level `old_value` / `new_value` list
- `metadata` — the JSON metadata recorded with the mutation
- `request` — the request log for the originating API call, or `null` when the change did not come from an API request

```bash
curl "API_HOST/v1/core/audit-events/auev_xxx?include[]=actor&include[]=changes&include[]=request" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Augno-Version: CURRENT_API_VERSION" \
  -H "Augno-Account: YOUR_ACCOUNT_ID"
```

```json
{
    "id": "auev_xxx",
    "object": "audit_event",
    "action": "update",
    "resource_type": "sales_order",
    "resource_id": "or_xxx",
    "actor": {
        "id": "us_xxx",
        "object": "actor",
        "type": "user",
        "name": "Jane Doe",
        "handle": "jane@example.com"
    },
    "changes": {
        "object": "list",
        "data": [
            {
                "object": "audit_field_change",
                "field": "customer_po_number",
                "old_value": "PO-1001",
                "new_value": "PO-1002"
            }
        ]
    },
    "occurred_at": "2026-05-14T17:04:11.812Z"
}
```

A `changes` entry has a `null` `old_value` on a creation event and a `null` `new_value` on a deletion event.

Field names in `changes` are the stored field names for the record, which are not always identical to the JSON field names on the corresponding API resource — a sales order's `customer_purchase_order_number` is audited as `customer_po_number`, for example. Treat `field` as a stable identifier for the changed column, not as a path into the API response body.

## Discovering the resource types you can filter on

`resource_types` and `root_resource_type` take object-type values. Rather than hard-coding that list into your integration, fetch it:

```bash
curl "API_HOST/v1/core/audit-events/resource-types" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Augno-Version: CURRENT_API_VERSION" \
  -H "Augno-Account: YOUR_ACCOUNT_ID"
```

The response is a flat list of plain strings, ready to drop into either filter — it is what the Dashboard's resource-type picker is populated from. It returns the complete set of object types the platform defines, so it stays current as new resource types ship. It does not tell you which of them actually have events in your account; use it to build a picker, not to summarize your history. See <InternalLink pathKey="apiReference.auditEvent.listAuditEventResourceTypes" text="List Audit Event Resource Types" />.

## Permissions

All three endpoints require two things, and both return `insufficient_permissions` when unmet:

- the `audit_events` read permission — see <InternalLink pathKey="manageAccount.team.rolesAndPermissions" text="Roles and permissions" />; and
- an **internal** identity for the account. Relation actors — a customer or supplier signed in against your account through the portal — cannot read audit events at all, regardless of the permissions on their role.

They also require the `Augno-Account` header naming the account whose history you are reading.

Calls to the audit-event endpoints are marked hidden in the request log, so paging through history does not flood the default <InternalLink pathKey="api.requestLogs" text="request-log" /> listing. The rows are still written — they are simply kept out of the way.

## Not the same thing as inventory change logs

<InternalLink pathKey="buildProducts.inventory.changeLogs" text="Inventory change logs" /> are a
separate, inventory-specific ledger: one row per stock movement, with the quantity delta and the
action that caused it. They are the right tool for "why did on-hand quantity drop by 40?".

Audit events are the general-purpose change history for API resources. Reach for audit events when the question is about a _record_, and for inventory change logs when the question is about _stock_.
