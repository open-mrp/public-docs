`GET /v1/core/search` runs one free-text term across many resource types at once and returns lightweight **entity references** — just enough to identify and link a record, not the record itself. It is the primitive behind pickers, `@`-mention menus, and omnibox-style search: fast, uniform, and permission-aware.

<BetaTag /> This endpoint is in **public preview**. It is live and documented here, but its shape
and its searchable-type list may change without notice before general availability — see
<InternalLink pathKey="releasePhases" text="release phases" />.

```bash
curl "API_HOST/v1/core/search?q=001" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Augno-Version: CURRENT_API_VERSION" \
  -H "Augno-Account: YOUR_ACCOUNT_ID"
```

```json
{
    "object": "list",
    "data": [
        {
            "id": "or_xxx",
            "object": "entity",
            "type": "sales_order",
            "name": "SO-001",
            "handle": "Acme Manufacturing"
        },
        {
            "id": "iv_xxx",
            "object": "entity",
            "type": "invoice",
            "name": "INV-001",
            "handle": "Acme Manufacturing"
        }
    ],
    "page_info": { "...": "..." }
}
```

Every result has the same four-field shape regardless of what it points at:

- `object` is always `entity` — this is a reference, not the resource.
- `type` names the resource the `id` points at.
- `name` is the display label: an order or invoice number, a customer name, an item SKU, an agent name.
- `handle` is a secondary identifier: the customer name on an order, the customer number on a customer, the item description on a product, the tracking number on a shipment.

For most types, acting on a result means fetching the underlying resource by `id` from that type's own endpoint. Two of the nine are exceptions:

- **`messaging_contact`** — the `id` is the **account-user** ID the contact maps to, not a contact ID, and contacts that map to no account user are skipped entirely. There is no retrieve-a-contact endpoint; messaging contacts are list-only, through `GET /v1/messaging/contacts`.
- **`agent_definition`** — the retrieve endpoint lives on the preview `/v1/ai` surface, which is not in the public OpenAPI specification and has no SDK method. Treat these results as display references unless you are already working against that surface.

## What gets searched

Nine resource types are searchable:

`sales_order`, `purchase_order`, `invoice`, `customer`, `item`, `product`, `shipment`, `messaging_contact`, `agent_definition`.

Each type is queried in parallel and the results are **interleaved round-robin** before being truncated to `limit`. That is deliberate: a short result list stays representative instead of being swallowed by whichever type happened to match most often. Because of the interleave, results are ordered by type rotation, not by relevance score.

If one type's backing service fails, that type simply contributes no results — the rest of the search still returns. A partial result set is not signalled in the response.

Search is single-page. `limit` caps the total number of entities returned (default `100`); `cursor` is accepted for interface consistency but there is no cursor to follow, so treat the response as the complete answer for that `limit`.

## Narrowing with `types`

Pass `types` to search a subset. Both forms work — repeated bracketed values or one comma-separated value:

```bash
curl "API_HOST/v1/core/search?q=acme&types=customer,sales_order" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Augno-Version: CURRENT_API_VERSION" \
  -H "Augno-Account: YOUR_ACCOUNT_ID"
```

```bash
curl "API_HOST/v1/core/search?q=acme&types[]=customer&types[]=sales_order" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Augno-Version: CURRENT_API_VERSION" \
  -H "Augno-Account: YOUR_ACCOUNT_ID"
```

Passing a value that is not one of the nine searchable types returns `parameter_invalid` on `types`. Note that the API reference advertises the platform's full object-type enum for this parameter; only the nine above are actually accepted.

## `q` is required unless you scope with `types`

An empty or omitted `q` returns `parameter_missing` — **unless** you also pass `types`. Scoped to one or more types, an empty query lists recent records of those types instead, which is what makes a picker useful before the user has typed anything.

```bash
# Recent sales orders, no search term.
curl "API_HOST/v1/core/search?types=sales_order&limit=8" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Augno-Version: CURRENT_API_VERSION" \
  -H "Augno-Account: YOUR_ACCOUNT_ID"
```

Unscoped and unqueried would mean "list everything, everywhere", so that combination is rejected.

## Permissions are applied per type

Search never returns a record the caller could not read directly. Each searchable type is gated on its own read permission:

| Type                | Required permission    |
| :------------------ | :--------------------- |
| `sales_order`       | `sales_orders:read`    |
| `purchase_order`    | `purchase_orders:read` |
| `invoice`           | `invoices:read`        |
| `customer`          | `customers:read`       |
| `item`, `product`   | `items:read`           |
| `shipment`          | `shipments:read`       |
| `messaging_contact` | `messaging:read`       |
| `agent_definition`  | `agents:read`          |

Types you cannot read are dropped from the fan-out. The practical consequences:

- A caller holding **none** of the permissions above gets `insufficient_permissions` (403) — the endpoint itself requires at least one of them.
- A caller who holds some of them and narrows `types` to only types they cannot read gets an **empty list**, not a 403. This is worth designing for: an empty result can mean "nothing matched" _or_ "you cannot see this type". If you need to distinguish the two, check the caller's role rather than inferring it from the response.

Because permissions are evaluated per request, the same query run by two different API keys can legitimately return different result sets.

## Customer-scoped search

Pass `customer` with a customer's account ID to restrict the search to that one customer **and** narrow the searched types to the ones that are safe to show a customer:

```bash
curl "API_HOST/v1/core/search?q=001&customer=ac_xxx" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Augno-Version: CURRENT_API_VERSION" \
  -H "Augno-Account: YOUR_ACCOUNT_ID"
```

In this mode only three types are searched — `sales_order`, `invoice`, and `shipment` — and each is filtered to records belonging to that customer. Every other type is excluded outright, even when the caller has permission to read it.

That combination is the point: it is a safe primitive for anything customer-facing. Use it when you are composing content a customer will see — a <InternalLink pathKey="generateSales.customerPortal" text="customer portal" /> search box, or a reply that tags a record — and you need a hard guarantee that no privileged record can be surfaced or linked by mistake. Filtering privileged results out on the client is not equivalent; here the server never looks them up.

`customer` and `types` can be combined, in which case the searched set is the intersection of your `types` and the three customer-safe types.

## Errors

| Code                       | When                                                                  |
| :------------------------- | :-------------------------------------------------------------------- |
| `parameter_missing`        | `q` was empty or omitted and `types` was not supplied                 |
| `parameter_invalid`        | `types` contains a value that is not one of the nine searchable types |
| `insufficient_permissions` | The caller holds none of the eight read permissions above             |
| `parameter_unknown`        | An undefined query parameter was supplied                             |
