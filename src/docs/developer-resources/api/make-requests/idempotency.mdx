Our APIs support idempotent requests, allowing you to safely retry requests without unintentionally executing the same operation more than once.

For endpoints that may create or mutate state (`POST` and `PATCH`), provide an idempotency key via the [`Idempotency-Key` header](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header). If something goes wrong (timeouts, transient errors, load shedding), you can retry with the same key.

## Which requests are idempotent?

- **Always idempotent**: `GET`, `PUT`, and `DELETE`
- **Idempotent with an idempotency key**: `POST` and `PATCH`

For `POST` and `PATCH`, we support idempotency via the `Idempotency-Key` header. This header has no effect on `GET`, `PUT`, or `DELETE` requests.

## Example

```bash
curl -X POST API_HOST/v1/finance/payment-terms \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Augno-Version: CURRENT_API_VERSION" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 6f1bd0d4-7bdc-4df9-9c77-4b1a61ff2f85" \
  -d '{"name": "Net 30"}' \
  -i
```

## How idempotency works

When the API receives a `POST` or `PATCH` with an `Idempotency-Key`, it looks the key up and lands in exactly one of four outcomes:

| Outcome                | What happens                                                                                        | Status                          |
| ---------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------- |
| **First use**          | The key is recorded and locked, your request executes, and the response is stored before it is sent | Whatever the endpoint returns   |
| **Replay**             | A stored response exists; it is returned byte-for-byte and nothing new executes                     | The original response's status  |
| **Still in progress**  | A request with this key is executing right now                                                      | `409` `idempotency_in_progress` |
| **Fingerprint change** | The key was used before with a different request fingerprint                                        | `400` `validation_failed`       |

Replayed responses include the header `Idempotent-Replayed: true`.

Because the response is persisted **before** it is written back to you, a duplicate request that arrives immediately after the first one will see a replay rather than a race.

## Failures that store, and failures that do not

Whether a retry re-executes or replays is decided by the **HTTP status** of the first attempt, not by the error body:

- **Status `429`, `500`, `502`, `503`, or `504` stores nothing.** The key's lock is released and no response is cached. The next request with that key is treated as brand new and runs the operation again.
- **Every other status is stored and replayed.** That includes error statuses: a `400`, `403`, `404`, or `409` becomes the cached response for that key. Retrying with the same key returns the same error, indefinitely. Fix the request and use a **new** key.

There is no partial resume. A retry after a released key re-executes the **entire** operation from the beginning — the API does not pick up where the previous attempt stopped. Design your payloads so that a full re-execution is what you want.

### Deterministic vs transient failures

Our standard error envelope includes an `is_transient` flag:

| `is_transient` | Meaning             | Retry Behavior                                                 |
| -------------- | ------------------- | -------------------------------------------------------------- |
| `false`        | Deterministic error | Do not retry; the same error will be replayed                  |
| `true`         | Transient error     | Retrying with the same idempotency key is safe and may succeed |

`is_transient` tells you **whether** to retry. The status list above tells you what the retry will actually do. They line up for the common cases, but they are separate mechanisms — so if you retry with the same key and get the identical error back carrying `Idempotent-Replayed: true`, that error was cached and no retry with that key will ever change it. Treat a replayed error as final and start over with a new key.

## What counts as the same request?

A request is treated as a replay of a prior request only when the **scope** matches. The scope is a hash of:

- the **idempotency key**
- the **HTTP method**
- the **route template** — for example `/v1/sales/customers/{id}`, not the expanded path
- the **acting principal** — the API key (or the signed-in user) that made the request
- the **target account** the request resolved to — the account named by `Augno-Account` when you send
  that header, and otherwise the account the credential itself belongs to

Reuse the same key against a different endpoint, method, API key, or target account and you get a fresh, unrelated record rather than a conflict.

> **The route template is not the concrete path.** A path parameter is not part of the scope and is not part of the fingerprint below. Sending the same key and the same body to `PATCH /v1/sales/customers/{id}` for two _different_ customers replays the first customer's response and silently never touches the second. Use one key per logical operation, not one key per retry campaign.

## Same key, same request fingerprint

Within a matching scope, the API also compares a fingerprint of the request. The fingerprint covers **both**:

1. The **JSON request body**, canonicalized first — whitespace and object key order do not matter, but array element order does.
2. The **query string** — the name of every query parameter, and the **first** value sent for each one.

That second point catches people out: reusing a key with an identical body but a changed query string — adding `?include[]=role` to a request that had no `include` at all, for instance — is a fingerprint change, not a replay.

> **Repeated parameters contribute only their first value.** `?include[]=role&include[]=role.permissions` fingerprints as `include[]=role`. Adding a _second_ `include[]` to a retry therefore does **not** change the fingerprint: the request replays the original, narrower response with `Idempotent-Replayed: true` rather than returning the wider expansion you asked for. If you need different expansions, use a new key.

A fingerprint change is rejected with a `400`:

```json
{
    "error": {
        "code": "validation_failed",
        "type": "idempotency_error",
        "message": "Idempotency key '6f1bd0d4-7bdc-4df9-9c77-4b1a61ff2f85' was used with different request parameters; use a new key.",
        "param": null,
        "doc_url": "https://docs.augno.com/api/errors#validation_failed",
        "is_transient": false,
        "quota": null,
        "request_log_url": "https://augno.com/dashboard/request-logs/rq_fbv1ygmybo3eauykr74"
    }
}
```

Generate a new key for a different logical operation or an updated payload.

## Concurrent requests with the same key

While the first request is still executing, the key is locked. A second request arriving with the same key does **not** queue behind it — it fails immediately:

```json
{
    "error": {
        "code": "idempotency_in_progress",
        "type": "idempotency_error",
        "message": "Request for the idempotency key '6f1bd0d4-7bdc-4df9-9c77-4b1a61ff2f85' is already being processed.",
        "param": null,
        "doc_url": "https://docs.augno.com/api/errors#idempotency_in_progress",
        "is_transient": true,
        "quota": null,
        "request_log_url": "https://augno.com/dashboard/request-logs/rq_fbv1ygmybo3eauykr74"
    }
}
```

Treat `409 idempotency_in_progress` as "wait and re-check", not as a hard failure: back off, then retry the same key to pick up the replayed response once the first request finishes. The lock expires after five minutes if the original request never completed.

## How long is an idempotency key honored?

We respect an idempotency key for **30 days** after the first request. Retries with the same key within that window are replayed. After 30 days the record is purged — use a new key for new attempts.

One exception: on the endpoints that establish a browser session (the ones whose responses set cookies), the record is kept for five minutes rather than 30 days. Server-to-server integrations authenticating with an API key are unaffected.

## Size limits

Two caps bound what idempotency can do for you:

- **Request body: 1 MiB.** A `POST` or `PATCH` carrying an `Idempotency-Key` and a body larger than 1 MiB is rejected outright rather than truncated.
- **Response body: 64 KiB.** To guarantee the record is durable before you see the response, the response is buffered as it is produced — and that buffer stops at 64 KiB.

> **Requests whose response exceeds 64 KiB are not protected by their idempotency key.** The buffered copy is cut at 64 KiB, so it is what gets returned to you _and_ what is offered for storage. A body cut mid-structure cannot be persisted, so nothing is cached: the key's record is never completed and its lock is never cleared. A retry with the same key returns `409 idempotency_in_progress` until the five-minute lock expires, and any retry after that re-executes the operation in full. This is the one case where the key does not prevent a duplicate write.

Keep write responses under the cap. Request fewer `include[]` expansions on `POST` and `PATCH`, then re-read the resource with a `GET` — which is idempotent on its own and has no such buffer — instead of relying on a large create or update response.

## Retrying safely

To avoid overwhelming the API when many clients retry after an outage:

- Use **exponential backoff with jitter**
- Honor `Retry-After` when present — see <InternalLink text="rate limiting" pathKey="api.rateLimiting" /> for how that value escalates
- Use `is_transient` to decide whether to retry:
    - `false` -> do not retry
    - `true` -> retry with the same idempotency key

## Conventions you can rely on

For endpoints that create or mutate state (specifically, `POST` and `PATCH`), include an idempotency key:

- **Request header:** `Idempotency-Key: <unique value>`

Recommendations:

- Generate the key client-side.
- Use a UUID v4.
- Keep it to 255 characters or fewer.
- Generate a new key for a new logical action — including for the same action against a different resource ID.
- Reuse the same key when retrying the same logical action (after timeouts).
- Idempotency is scoped per route template, per method, and per authenticated principal.

What you should expect:

- Repeating a request with the same key and the same fingerprint returns the same outcome.
- Replayed data may be stale if the resource has been modified after the first successful request.
- Conflicting fingerprints with the same key are rejected.
- A successful replay includes `Idempotent-Replayed: true`.
