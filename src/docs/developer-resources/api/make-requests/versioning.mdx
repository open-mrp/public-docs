Augno uses a versioning system designed to protect existing integrations while allowing the API to evolve. By specifying a version with each request, you control exactly which API behavior your integration targets. The current version is <ApiVersion />.

## The Augno-Version header

All API requests **require** the `Augno-Version` header. Requests without it are rejected with `400` and the error code `api_version_required`; requests naming a version the API does not support are rejected with `400` and `api_version_invalid`, and the message lists every version that is accepted.

```bash
curl API_HOST/v1/sales/customers \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Augno-Version: CURRENT_API_VERSION"
```

Every successful response echoes an `Augno-Version` header carrying the version the request was resolved to. Assert on it in your integration tests — it is the cheapest way to catch a client that forgot to pin.

## Version format

Versions follow the format:

`<minor>.<patch>.<codename>`

- **Minor** — Incremented for non-breaking feature additions
- **Patch** — Incremented for bug fixes and small improvements
- **Codename** — The major version identifier (e.g., `forge`, `crucible`)

For example, `1.0.forge` would be a stable release of the `forge` major version with minor version 1 and patch version 0.

## Preview releases

Preview releases let you work against upcoming changes before they are promoted to stable. Preview versions use the format:

`<minor>.<patch>.<codename>-preview.<n>`

For example, `1.3.forge-preview.1` is the first preview of what will become `1.3.forge`.

Preview releases:

- Are ordered numerically (e.g., `preview.1`, `preview.2`, `preview.3`)
- May contain breaking changes between preview numbers
- Are promoted to stable once finalized (e.g., `1.3.forge-preview.2` becomes `1.3.forge`)

> **Every currently supported version is a preview.** The API accepts <ApiVersion /> and the preview immediately before it. There is no stable `forge` release yet, so "pin to a stable version" is not an option you have today — pin to an explicit preview version, keep it in configuration rather than hard-coded, and plan for a breaking change when the next preview or the first stable release lands. Older previews are not withdrawn the moment a newer one ships; more than one preview is supported at a time.

## Breaking vs non-breaking changes

**Breaking changes** require a new codename:

- Removed fields or endpoints
- Changed field types or formats
- Changed authentication requirements
- Modified error response structures
- Renamed fields or endpoints

**Non-breaking changes** are released under new minor or patch versions:

- New optional fields in responses (minor)
- New endpoints (minor)
- New optional request parameters (minor)
- Bug fixes (patch)
- Performance improvements (patch)

## What pinning a version actually does

Pinning is not a routing decision — there is no separate copy of the API per version. The gateway always runs the newest code, and translates at the edge in both directions:

1. **Your version is resolved.** The header is parsed and checked against the supported set. Anything unrecognized is rejected before the endpoint runs.
2. **Your request is upgraded.** If you pinned an older version, your JSON request body is rewritten into the current shape before the endpoint sees it. Your integration keeps sending the shape it was written against.
3. **The endpoint runs against the current shape.** One code path, for every caller.
4. **Sub-objects the downgrade needs are expanded for you.** A translation may require data your version had no way to ask for. In that case the gateway resolves the necessary <InternalLink text="includes" pathKey="api.include" /> itself, on top of whatever you requested, so the downgrade has real values to work with. Nested expansions are only forced when you already asked for their parent — forcing them unconditionally would itself change the response shape.
5. **The response is downgraded.** The result is rewritten back into your pinned version's shape before it is serialized.
6. **The resolved version is echoed** in the `Augno-Version` response header.

A worked example: in <ApiVersion />, an `account_user` exposes `user` as an expandable full user object and no longer duplicates the user's `name`, `email`, `username`, and `image_url` onto itself. The previous preview carried those four fields directly on `account_user`. A caller pinned to that older preview never sends `?include[]=user` — it does not know the parameter exists — so the gateway expands `user` on its behalf, copies the four profile fields back onto `account_user`, and rebuilds the reference shape the older version returned. The caller sees exactly the payload it was written against.

Two consequences worth knowing:

- **Translation is per object type.** Only object types a translation was written for are rewritten. Everything else is passed through as-is, which is why a new field can appear in an old version's response — additive changes are not breaking and are not translated away.
- **Forced expansion costs latency.** Pinning an older version can make a request do more work than the same request on the current version, because sub-objects have to be resolved to satisfy the downgrade.

## Upgrading versions

When upgrading to a new version:

1. **Test in sandbox first.** Use the new version header in your sandbox environment to verify compatibility.
2. **Review the changelog.** Check for any changes that affect your integration.
3. **Watch the echoed header.** Confirm responses come back with the version you intended before you roll out.

### Preparing for codename migrations

When a new codename is released:

1. Review the migration guide for breaking changes
2. Update your integration to handle the new API behavior
3. Test thoroughly in sandbox
4. Update the `Augno-Version` header in production

We provide advance notice before deprecating old codenames and maintain overlap periods where both versions are supported.
