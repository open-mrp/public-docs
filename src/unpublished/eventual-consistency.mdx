Interactions with our APIs often require asynchronous work to be done in the background. As a result:

- Some operations are **asynchronous** (they finish after the HTTP response is returned).
- Some data is **eventually consistent** (related records may appear/settle shortly after the initial request succeeds).
- Clients must be prepared to **retry safely** using **idempotency**.

This article explains the patterns you will see across the API and how to integrate reliably.

## Key concepts

### Idempotency

An API call is _idempotent_ if repeating the same request does **not** create duplicate side effects.

Idempotency lets you **safely retry** a request without accidentally performing the same operation twice. For example, if a "create customer" request times out or the network drops, you can retry it without creating duplicate customers.

In a distributed system, retries happen for many reasons (timeouts, transient errors, load shedding). The API supports idempotency so you can retry without creating duplicates.

#### Which requests are idempotent?

- **Always idempotent by HTTP semantics**: `GET`, `PUT`, and `DELETE`
- **Idempotent when you include an idempotency key**: `POST` and `PATCH`

For `POST` and `PATCH`, we support idempotency via the [`Idempotency-Key` header](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header). This header has **no effect** on `GET`, `PUT`, or `DELETE`.

#### How it works

When the API receives a request with an `Idempotency-Key`:

1. It checks whether it has already processed a request with the same key.
2. If the first request **succeeded**, the API skips making new changes and returns a **replayed response**, including `Idempotent-Replayed: true` (the response may be updated to reflect the current state).
3. If the first request **failed (or partially failed)**, the API attempts to re-execute the failed operation(s) and returns the new response.
4. In rare cases where it's no longer possible for an idempotent replay to succeed, the API returns an error explaining why.

#### What counts as an idempotent replay?

A request is treated as an idempotent replay of a prior request when all of the following are true:

- **Same idempotency key** for the **same API endpoint**
- **Same account and environment**, such as sandbox vs production
- **Within the replay window**, up to 30 days apart

### Eventual consistency

When an operation touches multiple internal services, each service commits its own local database changes. The overall system converges to a consistent final state **over time**.

This means you may briefly observe intermediate states such as:

- A resource exists but some related fields/relations are not yet populated.
- A follow-up read immediately after a write may not reflect all downstream effects.
- A status may temporarily be `PENDING` / `IN_PROGRESS` before becoming final.

### Operations (asynchronous workflow tracking)

For requests that may take time or involve multiple steps, the API may return an **operation** that you can poll to learn when processing is complete.

## Conventions you can rely on

<DocNumberedSection number={1} title="Idempotency key (client-provided)" className="mt-6">
For endpoints that create or mutate state (especially `POST`), you should include an idempotency key:

- **Request header:** `Idempotency-Key: <unique value>`

**Client guidance**

- **Generate the key client-side**.
- **Use a UUID v4** (recommended) and reuse the same key when retrying the same logical operation.
- **Max length**: 255 characters.
- Generate a new key for a _new_ logical action.
- Reuse the **same** key when retrying the _same_ logical action (including after timeouts).
- Idempotency is scoped per endpoint and per authenticated principal.

**What you should expect**

- Repeating a request with the same key returns the same outcome.
- Conflicting payloads with the same key may be rejected.
- A successful replayed response will include `Idempotent-Replayed: true` in the response headers.

**Example**

```bash
curl -X POST API_HOST/v1/core/customers \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 6f1bd0d4-7bdc-4df9-9c77-4b1a61ff2f85" \
  -d '{"name":"Acme Corp"}' \
  -i
```

If you retry the exact same operation with the same `Idempotency-Key`, a successful replayed response will include:

```http
Idempotent-Replayed: true
```

</DocNumberedSection>

<DocNumberedSection number={2} title="Request and correlation identifiers">
Responses may include:

- `X-Request-Id`
- `X-Correlation-Id`

Log these values for troubleshooting.

</DocNumberedSection>

<DocNumberedSection number={3} title="Asynchronous responses">
Some endpoints return before processing completes. You may see:

- HTTP `202 Accepted`
- An `operation_id`
- A `Location` header pointing to an operation status endpoint
- `Retry-After`

</DocNumberedSection>

<DocNumberedSection number={4} title="Operation status model">
Operations typically transition through:

- `PENDING` / `IN_PROGRESS`
- `SUCCEEDED`
- `FAILED`

Terminal states indicate completion.

</DocNumberedSection>

<DocNumberedSection number={5} title="Resource-first pattern">
Some endpoints return a resource immediately with a non-final status:

- `PENDING`
- `PROCESSING`

Treat these as valid intermediate states and poll until terminal.

</DocNumberedSection>

## How to integrate safely

<DocNumberedSection number={1} title="Always use idempotency keys">
Send an idempotency key for all non-read operations. Reuse the same key when retrying.

</DocNumberedSection>

<DocNumberedSection number={2} title="Avoid read-after-write assumptions">
If an operation is asynchronous, poll the operation or resource status before proceeding.

</DocNumberedSection>

<DocNumberedSection number={3} title="Expect temporary gaps">
You may temporarily see missing data or `404`s while changes propagate. Retry with backoff.

</DocNumberedSection>

<DocNumberedSection number={4} title="Handle duplicates and in-progress responses">
Treat repeated `202`, `200`, or conflict responses as non-fatal if intent is unchanged.

</DocNumberedSection>

## Retry recommendations

- Use exponential backoff with jitter
- Retry on transient failures
- Do not retry validation errors unless the request changes
- Reuse idempotency and correlation identifiers

---

## What this means for atomicity

- Single-service operations are transactional
- Multi-service operations rely on idempotency and eventual convergence
- Intermediate states are safe and observable

---

## How to recognize these patterns

Look for:

- `202 Accepted`
- `operation_id`
- `Location` headers
- Non-terminal resource statuses

These indicate asynchronous processing and eventual consistency.
